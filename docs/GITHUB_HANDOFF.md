# GitHub handoff and new-chat prompt

This file is written for the next GitHub-connected chat or coding agent. It is deliberately self-contained enough to prevent the audit decisions from being lost when the conversation changes.

## Repository import

The archive should be uploaded as a normal source repository, not as a release binary. From a local machine:

```bash
unzip agentforge-mvp.zip
cd agentforge

git init -b main
git add .
git commit -m "chore: import verified AgentForge MVP"
git remote add origin https://github.com/OWNER/REPOSITORY.git
git push -u origin main
```

If the GitHub repository already has a README or another root commit, clone it first and copy the archive contents into that clone instead of creating unrelated history. Do not upload `.env`, database files, private keys, caches, or generated bytecode.

## Copy-paste prompt for a GitHub-connected chat

```text
You are continuing the AgentForge repository from the uploaded baseline.

Read README.md, docs/PROJECT_STATUS.md, docs/AUDIT_VERIFICATION.md,
docs/ARCHITECTURE_DECISIONS.md, docs/PR_PLAN.md,
AGENTFORGE_ARCHITECTURE.md, and ANTIGRAVITY_IMPLEMENTATION_BRIEF.md before
changing anything.

Treat the audit-fix MVP as frozen and preserve its current tests and protocol
contract. The current baseline has passed 16 tests, compile checks, JSON Schema
checks, OpenAPI synchronization, and a SQLite Alembic upgrade/downgrade/upgrade
round trip. PostgreSQL still needs a real integration run.

The first implementation task is only to extract the existing local escrow
behavior behind SettlementProvider and MockSettlementProvider without changing
mock semantics. Keep MOCK and TEST_CREDIT as the only local assets, reject FLOP
assets in the local provider, and do not invent FLOP contracts, receipts, fees,
eligibility, airdrop scoring, or TCLK cryptography. Do not add arbitrary external
agent execution. Keep deployment/network mode and activity eligibility
server-derived, not client-selected.

Before coding, inspect the existing routes, services, models, tests, and protocol
schemas. Propose the smallest file-level change and a focused test plan. Make
one small branch/PR at a time. Run the full verification commands from
docs/AUDIT_VERIFICATION.md before presenting a commit.
```

## Branch and commit workflow

Use one branch per cohesive change:

```bash
git switch -c refactor/settlement-provider-boundary
python -m pytest -q
python -m compileall -q server sdk tests examples
# inspect the diff and update docs/protocol only if the public contract changed

git diff --check
git add server tests docs
git commit -m "refactor: isolate mock settlement provider"
git push -u origin refactor/settlement-provider-boundary
```

Use imperative Conventional Commit-style subjects such as:

- `chore: import verified AgentForge MVP`
- `docs: record frozen settlement boundary`
- `refactor: isolate mock settlement provider`
- `test: cover unsupported local settlement assets`
- `feat: persist external deal references`
- `feat: add gated TCLK coordination adapter`

Do not combine a provider refactor, a protocol migration, and an external-network integration in one PR.

## Pull request expectations

Every PR should state:

- the problem and the smallest intended change;
- files/routes/models affected;
- whether the public API or JSON Schemas changed;
- migration and rollback impact;
- authorization/idempotency implications;
- exact test and verification commands;
- explicit non-goals, especially anything involving FLOP or airdrop behavior.

Use `.github/pull_request_template.md` as the starting checklist.

## First future PR acceptance criteria

The first provider-boundary PR is complete only if:

- existing mock escrow tests pass unchanged or with only test helper imports adjusted;
- `FULL_RELEASE`, `PARTIAL_RELEASE`, `REFUND`, and `SLASH` remain idempotent and mutually exclusive;
- Decimal/string accounting and audit/ledger event behavior are unchanged;
- local settlement rejects `FLOP` rather than silently treating it as `MOCK`;
- no client request can select a deployment/network mode;
- no new external protocol assumption appears in the schema;
- docs state that mock settlement is not official FLOP activity;
- the complete verification commands pass.

## Stop conditions

Stop and ask for explicit scope approval if a proposed change needs any of the following:

- a real FLOP endpoint, contract address, receipt format, fee schedule, or campaign formula;
- new cryptography or a custom payment channel;
- client-selected eligibility or network mode;
- automatic task/volume generation for reputation or airdrop purposes;
- arbitrary code execution in the API;
- a large economic/validator system beyond fixed MVP behavior.
